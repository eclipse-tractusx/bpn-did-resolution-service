# Migration Guide `0.6.x -> 0.7.0`

This document outlines the necessary changes for migrating your bdrs installation from versions 0.6.x to 0.7.0.
It also outlines some points that adopters and operators should pay close attention to when migrating from one version
to another.

This document is not a comprehensive feature list.

## 1. EDC Version

BDRS is now built on EDC `0.18.2` instead of `0.16.1`. The behavioural changes BDRS inherits from EDC `0.17.x` and
`0.18.x` are listed below. The database schema, the datasource configuration (`edc.datasource.didentry.*`) and the
HashiCorp Vault configuration (`edc.vault.hashicorp.*`) are unchanged.

## 2. Stricter Verifiable Presentation validation

Clients of the Directory API authenticate with a Verifiable Presentation (VP) sent as a JWT in the `Authorization`
header. The following VPs, which could previously pass, are now rejected with `401 Unauthorized`:

- **VPs without credentials.** A VP whose `verifiableCredential` is missing, `null` or an empty array is rejected by
  BDRS before credential validation runs.
- **VPs with an ambiguous format** (EDC [#6214](https://github.com/eclipse-edc/Connector/pull/6214), shipped in
  `0.18.2`). A JWT presentation must match exactly one format: VCDM 1.1 (a `vp` claim) or VCDM 2.0 (the VCDM 2.0
  `@context`). VCDM 2.0 JOSE presentations must contain the VCDM 2.0 `@context`.
- **VPs that nest anything other than credentials.** Entries inside a presentation must be credentials; a nested
  presentation is no longer accepted.
- **Malformed VPs.** Any unexpected error while parsing or validating a presentation now results in `401` instead of
  an error response.
- **Empty `Authorization` header values.** A request whose `Authorization` header is present but has no value now
  results in `401` instead of an error response.

Connectors that send a regular VCDM 1.1 JWT presentation containing a valid MembershipCredential are not affected.
Clients that build presentations themselves should check that they include the credentials and the correct format.

## 3. Optional `holder` in Verifiable Presentations

The `holder` property of a presentation is now optional (EDC [#5697](https://github.com/eclipse-edc/Connector/pull/5697)):

- For VCDM 2.0 JOSE presentations, the holder is read from the `holder` claim instead of the `iss` claim.
- If a presentation has no `holder`, the check that credential subjects match the holder is not applied.

The signature of the presentation and of every contained credential is still verified, and a valid MembershipCredential
from a trusted issuer is still required.

## 4. Deprecated configuration keys

The following keys were renamed in EDC `0.17.0`. The old keys still work, but they may be removed in a future EDC
version. For the trusted issuer keys, EDC logs a deprecation warning at startup
(`Using deprecated configuration prefix 'edc.iam.trusted-issuer'`); `edc.iam.issuer.id` is accepted without a warning.

| Old key (deprecated)                          | New key                                     | Environment variable (new)              |
|-----------------------------------------------|---------------------------------------------|-----------------------------------------|
| `edc.iam.trusted-issuer.<alias>.id`           | `edc.iam.trustedissuer.<alias>.id`          | `EDC_IAM_TRUSTEDISSUER_<ALIAS>_ID`      |
| `edc.iam.trusted-issuer.<alias>.properties`   | `edc.iam.trustedissuer.<alias>.properties`  | `EDC_IAM_TRUSTEDISSUER_<ALIAS>_PROPERTIES` |
| `edc.iam.trusted-issuer.<alias>.supportedtypes` | `edc.iam.trustedissuer.<alias>.supportedtypes` | `EDC_IAM_TRUSTEDISSUER_<ALIAS>_SUPPORTEDTYPES` |
| `edc.iam.issuer.id`                           | `edc.participant.did`                       | `EDC_PARTICIPANT_DID`                   |

The provided helm charts still set the deprecated keys (`EDC_IAM_TRUSTED-ISSUER_<n>-ISSUER_ID`, `EDC_IAM_ISSUER_ID`),
so no action is needed for installations using the charts. Operators who configure BDRS directly should switch to the
new keys.

## 5. Custom runtimes

This section only applies to adopters who assemble their own runtime from the BDRS modules instead of using the
provided `bdrs-server` or `bdrs-server-memory` images.

- The EDC module `participant-context-single-core` was removed. Use `participant-context-connector-classic-core`
  together with `participant-context-core` instead. Unlike the removed module, these no longer provide a default
  `ParticipantIdentityResolver`. BDRS does not use it, but custom extensions that inject it must now provide one.
- The EDC DCP core extension now requires a `DiscoveryService`, which EDC only implements in the connector control
  plane. Add the BDRS module `extensions:noop-discovery`, which provides a no-op implementation. BDRS does not perform
  DSP protocol discovery.
